# RocketWiki docs site

Astro [Starlight](https://starlight.astro.build/) site generated from the
canonical repo docs.

**Not published anywhere.** It used to deploy to GitHub Pages on every push to
`main`, which put a public site describing a private repository's design on the
internet. That was removed and the Pages site unpublished.
`.github/workflows/docs.yml` still builds it and runs `--check` on every push
that touches the generation inputs — the link check is the only thing guarding
design.md's `§`-references from rotting — but it uploads nothing. Run the site
locally with `npm run dev`.

## The one rule: the site never forks content

`design.md` is the constitution, `README.md` the status ledger, and
`DEVELOPING.md` / `data-model.md` / `deploy/README.md` /
`src/RocketWiki.AppHost/keycloak/README.md` the operational docs — **all of
them stay canonical at their repo locations**. This site is a build-time
view of those files, regenerated on every `dev`/`build`:

| Source (canonical — edit these) | Generated page(s) |
|---|---|
| `design.md` | `design/00-overview` + one page per `## N.` section (`design/NN-slug`) |
| `README.md` → "Current status" section | `status` |
| `DEVELOPING.md` | `developing` |
| `data-model.md` | `data-model` |
| `deploy/README.md` | `operations/deploy` |
| `src/RocketWiki.AppHost/keycloak/README.md` | `operations/keycloak` |

Everything the generator writes under `src/content/docs/` is **gitignored**
(same discipline as `web/`'s GraphQL codegen). The only hand-written,
committed pages are `src/content/docs/index.mdx` (landing) and
`docs-map.md` (the documentation map).

## How generation works

`scripts/generate.mjs` (run automatically via `predev`/`prebuild`):

1. Splits `design.md` at each `## N. Title` heading into one page per
   section, zero-padded (`design/07-audit-logging`) so filename order is
   section order for the autogenerated sidebar. Subheadings are promoted one
   level (`###` → `##`) so each page has a proper outline; anchors are
   unaffected (ids derive from heading text).
2. Imports the other documents whole, with the H1 becoming the frontmatter
   title.
3. **§-reference pass** (best effort): `§N`, `§N.M`, and `design.md §N` in
   prose become links to the split pages — with a heading anchor when a
   numbered subsection heading (`### 6.7 …`) exists, section-top otherwise.
   References inside code fences, inline code, or existing links are left
   alone; a section number that doesn't exist stays plain text. The script
   prints exactly what it linked, fell back on, and skipped.
4. **Repo-link pass**: relative links are resolved against the source file's
   directory, then rewritten to the site page when the target is one of the
   generated documents, or to a `github.com/...:/blob/main/` URL otherwise.
5. Fails loudly (non-zero exit) if any source is missing, the design split
   finds zero sections, README has no "Current status" section, or any
   generated/curated internal link points at a page or anchor that doesn't
   exist.

`node scripts/generate.mjs --check` runs everything except the write step —
CI runs it before building. `npm test` unit-tests the transformation logic
(`scripts/lib.test.mjs`, plain `node:test`).

## Adding or changing content

- **Change documentation** → edit the canonical file listed above. Each
  generated page names its source at the top.
- **A new `## N.` section in design.md** → appears automatically; nothing to
  configure.
- **A new canonical document** → add it to `SOURCES` + the import list in
  `scripts/generate.mjs`, the `pageMap` (so links to it rewrite), the
  sidebar in `astro.config.mjs`, and the gitignore block for its output
  path.
- **Curated content** → only if it's genuinely site-native (navigation,
  orientation). Anything that states facts about the system belongs in the
  canonical docs, where the people building the system will keep it honest.

## The base path (read before touching links)

The site is built for a *project site* base path of `/RocketWiki/` — kept as it
was rather than flattened to `/`, so that re-publishing is re-enabling a
deployment rather than reworking every link.
`scripts/site-constants.mjs` is the single source of truth for `site`,
`base`, and the repo URL — `astro.config.mjs` and the generator both import
it. Generated links are emitted base-prefixed; the two curated pages
hardcode `/RocketWiki/...` links, and `--check` validates those too.

## Local commands

```sh
npm ci
npm run dev      # generates content, then Astro dev server (under /RocketWiki/)
npm run build    # generates content, then builds to dist/
npm run check    # validate generation without writing
npm test         # unit tests for the generator logic
```
